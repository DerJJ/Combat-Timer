# AGENTS.md — Technical Reference

This file describes the current architecture of the project for anyone (human or AI) picking it up cold. It intentionally omits rationale, history, and future plans — just what exists and how it fits together.

## What this is

- A single-file Tampermonkey **userscript** (`foundry-combat-timer.user.js`) for Foundry VTT. Not a Foundry module — it is never installed via Foundry's module manager, never appears in "Manage Modules", never touches `game.settings`.
- Plain IIFE, no build step, no dependencies, no imports. Everything lives in one file.
- Target: Foundry VTT **v13 and v14** (v14 is primary). Uses v13/v14-era APIs: the `Color` class (`user.color.css`), `Document#testUserPermission`, the record-based `getSceneControlButtons` shape (`controls.tokens.tools` / a top-level `SceneControl` with `tools`/`activeTool`), ApplicationV2-style `render({force: true})`.
- Tuned for the **dnd5e** and **pf2e** systems specifically where system-dependent assumptions were needed (e.g. actor types), but most logic is system-agnostic.

## Hard constraints

These are invariants the code must keep satisfying, not just current behavior:

1. **Client-side only.** No server writes. No `game.settings.register` (its intended timing — the `init` hook — is generally already past by the time a `document-idle` Tampermonkey script attaches; local persistence is `localStorage` instead).
2. **Anything visible to other connected clients must be self-contained.** Concretely: all HTML passed to `ChatMessage.create` must use fully inline `style="..."` with `!important` on every color/background/border declaration, and must never reference an externally injected `<style>` tag, CSS class, or anything else that depends on the *viewer* also having this script. This must render identically for someone who has never heard of this script, in both Foundry's light and dark theme. (`<table>` was deliberately abandoned for chat content in favor of flexbox `<div>`s — Foundry's/system's own table styling kept leaking through even with `!important`-hardened cells.)
3. **`combatStart` cannot be trusted alone** to signal a genuinely new encounter (reset-and-restart of the same Combat document, hook ordering, etc.). Session-boundary detection is done by comparing the live `Combat#id` against the last known one on tracked data (see "Session boundary detection" below), independent of which hook fires.
4. **The panel itself must never depend on anything experimental or version-sensitive.** `buildPanel()` (called as `panel = buildPanel()` against a pre-declared `let panel = null`, see Rendering) must remain the first thing that can possibly fail-safe; nothing else in `init()` is allowed to run before it if there's any chance it could throw. This script attaches via `@run-at document-idle`, i.e. strictly after Foundry's own core boot sequence — hooks that only fire once during that early boot (e.g. `getSceneControlButtons`, confirmed by logging: it never fires for a listener registered this late, and `ui.controls.render()` does not re-invoke it) are permanently unreachable from here and should not be relied on. The floating `⚔️` reopen button (`buildReopenButton()`, fixed position left-middle) is therefore the only entry point back into a closed panel — there is no scene-controls toolbar integration.

## Bootstrap

`waitForFoundryReady()` polls for `window.Hooks` to exist, then either calls back immediately if `game.ready` is already true or waits for `Hooks.once("ready", ...)`. This handles the race between Tampermonkey's `@run-at document-idle` firing before vs. after Foundry's own boot sequence — by the time our script attaches, Foundry's early lifecycle hooks (`init`/`setup`/`ready`) may already have fired.

## Data model

### Segment

The atomic unit of tracking — one contiguous slice of time with a single technical identity and a category. Segments are plain JSON-serializable objects (persisted via `JSON.stringify`).

```
{
  id: string,
  start: number,          // Date.now() timestamp
  end: number | null,     // null while running
  trigger: "turn" | "pause" | "unpause" | "resume" | "split",
  combatId: string | null,      // Combat document id, for session-boundary detection
  round: number | null,         // combat.round at creation time - not reconstructable later from timestamps (pauses/splits/reloads break that)
  turnIndex: number | null,     // combat.turn at creation time (0-indexed turn-order position); Foundry rounds themselves are 1-indexed
  combatantId: string | null,   // Combatant document id
  combatantName: string,
  actorId: string | null,       // Actor document id - stable across the encounter (and across sessions), unlike combatantId; not consumed anywhere yet
  actorType: string | null,     // combatant.actor.type, raw - see isPcActorType() for what counts as a real PC vs. a player-owned summon/pet, used by isRealTurn()
  ownerId: string | null,       // Foundry User id of the owning player; null = true NPC/monster
  overrideOwnerId: string | null, // manual reassignment target; wins over ownerId when set
  defeated: boolean,              // combatant.isDefeated, snapshotted at segment creation
  category: "player" | "gm" | "team" | "setup" | "ignore",
}
```

### Session and history

```js
segments: Segment[]          // current session, closed segments
currentSegment: Segment|null // current session, the running one
archiveManifest: { id: string, startedAt: number, endedAt: number }[]  // newest first, capped at ui.maxArchivedSessions
```

Three kinds of localStorage keys, each an independent read/write unit so a live-tracking write never has to touch archived data and vice versa:

- `ctp-state-<world.id>-<user.id>` — `{ v: 1, segments, currentSegment }`, the live session only.
- `ctp-state-archive-index-<world.id>-<user.id>` — `{ v: 1, sessions: archiveManifest }`, the small manifest listing every archived session (id/startedAt/endedAt only, not their segments).
- `ctp-state-archive-<world.id>-<user.id>-<id>` — `{ v: 1, segments }`, one key per archived session, named by its manifest id.

`v` exists so a future schema change has a way to tell "this data predates versioning" from "this field is legitimately absent" — nothing currently reads or branches on it; it's a placeholder for exactly one future migration decision, not a general migration framework. **Scope is per-browser, per-Foundry-world, per-Foundry-user.** The user-id component exists specifically so two different Foundry accounts logged in from the same physical browser (e.g. a GM previewing a player account in a second tab) don't collide on the same storage key — Foundry only prevents two concurrent logins as the *same* account, not two different ones from one browser. There is no sync between different users' copies of this script — a GM and each player all have entirely independent tracking state. The only cross-client communication is the static HTML snapshot posted via chat reports; nothing feeds back from chat into tracking.

`viewedArchive` (`{ id, segments } | null`) is a lazily-loaded, single-entry in-memory cache of whichever archived session is currently selected — `getSelectedSessionData()` loads it on demand via `ensureViewedArchiveLoaded()` (skipped when the cache already matches `selectedSession`) rather than keeping every archived session's segments in memory at once, since the manifest can hold arbitrarily many. `invalidateViewedArchive(id)` clears it after a write that bypassed the cached object directly (import, undo, eviction), forcing a fresh reload on the next access. Three dirty flags gate `persist()`'s three writes: `liveDirty` (segments/currentSegment), `manifestDirty` (archiveManifest itself — archive/evict/delete/import metadata), and `archiveDirty` (`viewedArchive.segments` mutated in place, e.g. a category/owner reassignment on an archived segment — see `markSelectedSessionDirty()`). A one-off action like archiving, importing into an archived session, or undoing that import writes that session's own key immediately via `writeArchivedSession()`/`localStorage.removeItem()` rather than going through a dirty flag, since those are never the per-tick `renderPanel()` path.

`ui.maxArchivedSessions` (default 10, adjustable via the −/+ stepper in the "Archived" session list) caps `archiveManifest`'s length. `enforceArchiveCap()` evicts the oldest entries (and deletes their storage keys) past the cap, both right after a new session is added and immediately when the cap is lowered — a toast names which session was removed. Persisted UI state (see Rendering below), not tracking data, so a corrupt/absent UI key can't affect how much history is kept, only what the currently-configured limit is (falls back to the default).

`selectedSession` (`"current"` or an archived session's id) is pure UI state controlling what `getSelectedSessionData()` / `allSegments()` return for display and chat-report purposes. It never affects what's actually being tracked live — that always follows `game.combat` / `game.paused` regardless of what's on screen.

## Segmentation: what creates/closes a segment

Every segment, wherever it's built (real tracking, a split, dummy data), goes through `makeSegment(overrides)` — one function defining the default value for every field. A caller only specifies what's actually different from "nothing"; adding a new field later means adding it once, here, rather than hunting down every place a segment literal is built by hand.

- `Hooks.on("combatStart" | "updateCombat" [turn/round changed])` → `switchTurn(combat)`
- `Hooks.on("pauseGame")` → pause/unpause, but only if `game.combat` currently exists (pausing outside combat is not tracked). A pause segment shorter than `SHORT_PAUSE_MERGE_THRESHOLD_MS` (3s) never makes it into `segments` at all — `closeSegment()` folds it into whatever ran immediately before instead, on the assumption that a pause that brief is toggle lag or a misclick, not a real interruption.
- `Hooks.on("deleteCombatant")` → if the deleted combatant is the one `currentSegment` is tracking (some modules auto-delete a combatant the moment it's defeated, instead of just flagging it and leaving it in the tracker), the segment is marked `defeated: true` *before* `reconcileWithLiveState()` closes it out — same treatment as a combatant that was already defeated when its segment was created.
- Script (re)load → `reconcileWithLiveState()`: compares whatever was persisted against the actual live Foundry state (active combatant id + pause state). If it matches, the persisted `currentSegment` is left running untouched (including its original `start` time). If not, it's closed out and a fresh segment opened with trigger `"resume"`.
- Manual split (✂️ button) → `splitCurrentSegment()`: copies the running segment's fields (before `closeSegment()` mutates it), then closes it and opens a new one via `makeSegment({ ...carryOver, id, start, end: null, trigger: "split", overrideOwnerId: null })` — carries over everything (technical identity, category — a split is a continuation, not a reclassification, so it does not run back through `defaultCategory()`) except identity/timing and `overrideOwnerId`, which is explicitly reset: a split does not inherit a manual reassignment, it reverts to the technical owner.
- Manual category/player reassignment: mutates an existing segment's `category`/`overrideOwnerId` in place (no new segment created).

Only triggers `"turn"` and `"resume"` mark a genuinely new turn boundary (see `isTurnStart()` in Timing statistics) — never `"pause"`, `"unpause"`, or `"split"`, since those are continuations of an already-counted turn rather than new ones. `"resume"` counts because, by construction, `reconcileWithLiveState()` only ever creates one when live state does *not* match what was persisted — meaning it always represents either a genuinely new turn discovered after a reload, or a turn change missed while reloading. Either way it hasn't been counted anywhere else.

## Session boundary detection

`switchTurn(combat)`:
```js
const newCombatId = combat?.id ?? null;
const hasExistingData = !!currentSegment || segments.length > 0;
const knownCombatId = currentSegment?.combatId ?? segments.at(-1)?.combatId ?? null;
if (newCombatId && hasExistingData && knownCombatId !== newCombatId) archiveSessionIfNeeded();
```
A mismatch — including "no `combatId` recorded at all" (e.g. data persisted before this field existed) — triggers archival. This runs identically from both `combatStart` and `updateCombat`, so a new encounter is caught regardless of which hook actually fires for it.

`archiveSessionIfNeeded()`: closes the running segment, and if `segments` is non-empty, calls `addArchivedSession(segments[0].start, Date.now(), segments)` — writes the archived session to its own storage key and unshifts `{id, startedAt, endedAt}` onto `archiveManifest`, then `enforceArchiveCap()` evicts the oldest entries past `ui.maxArchivedSessions` — then resets `segments`/`currentSegment` and forces `selectedSession = "current"`.

## Categorization & attribution

Five categories: `player`, `gm`, `team`, `setup`, `ignore`.

- **`"setup"` is GM-only** — it means "the GM's own logistics/administrative time" (rules lookup, prep between encounters), and only makes sense when no player owns the segment. A segment with a player owner (`ownerId` at creation, or `resolvedOwner(seg)` afterward) can never be `"setup"` — not by default, not by inheritance, not via the manual picker (`categoryPickerHTML()` omits the chip entirely in that case).
- **Default on creation** (`defaultCategory(trigger, prevSegment, ownerId)`): for every trigger except `"pause"`, `"player"` if `ownerId` is set, otherwise `"gm"` — a genuinely unowned combatant's own turn is the GM's by default, not "player" (see `effectiveOwner()`/`countsForGM()` below for how a manual `"gm"` recategorization or a defeated-combatant redirect still resolve correctly on top of this). For `"pause"`: if there's no player owner and the segment right before it lasted under 5 seconds (likely a pause right at a round boundary, before anyone actually started deciding anything), default to `"setup"`; otherwise carry over the previous segment's category, unless that would hand `"setup"` to a now player-owned segment, in which case it falls back to `"player"` instead (assume genuine mid-decision interruption) — note this carry-over can still leave a `"player"`-category, unowned pause segment behind (e.g. inheriting from whatever ran before a monster's turn), which `countsForGM()` still has to account for. `defaultCategory()` never returns `"ignore"` — it's manual-only.
- **`"ignore"`**: for a segment that's really just a wall-clock gap, not real time — e.g. everyone logs off mid-session and resumes days later. `reconcileWithLiveState()` only closes/reopens a segment when the *live* Foundry state changed, so a stale multi-day-old segment isn't automatically cut off on reload if nothing about the actual combat state moved while everyone was away. The fix is manual: use the split (✂️) button to cut the segment right now (carrying over its identity, so tracking continues normally afterward), then recategorize the now-closed, days-long segment to `"ignore"` via the segment list. An `"ignore"` segment doesn't need any special-case exclusion in `perCombatantStats()`/`npcAggregate()`/`gmTotalStats()`/`categoryTotals()` — it simply never matches `"player"` or `"gm"`, so it's already invisible to all of them. It does need two structural changes: `buildTurnSlots()` skips it entirely (never becomes part of a slot, and forces whatever comes after it to start a fresh slot, so a real turn split across the gap doesn't get double-counted or have its slot corrupted by the gap's duration), and `sessionTotalMs()`/`absoluteWaitStats()` explicitly subtract its duration from their spans — excluding it from a min/max span calculation doesn't shrink anything by itself, since the segments before and after it still anchor the same start/end.
- **`hasCombatContext(seg)`**: `!!seg.combatantId` — the single gate every aggregate uses for "does this segment have real combat context at all" (a pause with no active combatant, for instance, does not).
- **`resolvedOwner(seg)`**: `seg.overrideOwnerId ?? seg.ownerId ?? null` — raw, single-segment resolution, no history. Used where the *technical* identity must stay technical: `buildTurnSlots()`'s `designatedOwner`, and the segment list's 🧑/👹 icon (a deliberately unsmoothed, technical/audit view).
- **`isPlayerControlled(seg)`**: `resolvedOwner(seg) !== null` — derived, not stored. There is no persisted `isPC` field; it used to be frozen at segment creation (`ownerId !== null`) and went stale the moment a segment was reassigned via `overrideOwnerId`. Old persisted data may still have an `isPC` field on disk — it's simply ignored on load, no migration needed since it was always derivable.
- **`getDummyPlayerSource()`** (dummy-data preview, loaded via the ⋯ menu only when the current session is empty): uses every real (non-GM) `game.users` entry there is — not capped at 3 — and pads up to 3 total with synthetic placeholder players (`Aria`/`Boro`/`Cass`) when there aren't enough real ones. A synthetic player's `ownerId` is `dummy-owner-<Name>`, which never collides with a real Foundry user id.
- **Unresolvable owner ids**: `ownerName(id)`/`getCombatantColor(id)` are the only two places that turn an `ownerId` into something displayable, and both fall back gracefully when `id` isn't a real, currently-known Foundry user — a synthetic dummy-data id from the above, or a real id from an imported session that isn't in this world's roster (a player who left, or data imported from a different game). `ownerName()` recovers a dummy id's name straight out of the id string, and otherwise falls back to a short id-derived placeholder (`Player ab12`); `getCombatantColor()` derives a stable color from a hash of the id (`hashToHex()`) instead of a flat grey. Both are pure functions of the id — no cache, no persisted state — so the same unresolvable id always renders the same way, including after a reload.
- **`isRealTurn(seg)`**: `hasCombatContext(seg) && (!seg.defeated || isPcActorType(seg.actorType))`. A defeated PC still gets a real turn (death saves etc. are genuine activity); a defeated NPC's turn is an instant skip — nobody decided anything, so it never counts as "a turn" for averaging, regardless of who its time ends up credited to. `actorType` is captured at segment creation the same way `actorId` is (`combatant?.actor?.type ?? null`); also used by `buildBarsContent()`'s `orderAndShade()` to find a player's own PC among their controlled entities. `isPcActorType(actorType)` (`=== PC_ACTOR_TYPE`, currently `"character"`) is the one place that knows what counts as "a real PC" for the dnd5e/pf2e systems this script currently supports — a future system needs only its own value added there, not a hunt through every call site.
- **`lastLiveOwnerByCombatant()`**: for each `combatantId`, who `resolvedOwner()` credited its most recent `isRealTurn()` segment to. Recomputed fresh every call (not cached), so it always reflects the latest data, including a manual reassignment made after the fact.
- **`effectiveOwner(seg, lastLiveOwner)`**: like `resolvedOwner()`, with two differences on top. First, a defeated NPC's instant-skip inherits whoever owned its last real turn (possibly nobody, i.e. unclaimed) instead of always reading as unclaimed itself — this is what makes a dead monster's leftover time redirect to whoever it was last reassigned to (as that player's `outOfTurnMs`, same mechanism as an Attack of Opportunity) — or, if it was never claimed, land in the GM/Monsters bucket — instead of silently disappearing. Second, `seg.ownerId` is only consulted when `category !== "gm"` — a manual `"gm"` recategorization always wins over the segment's own technical owner (that's the entire point of flagging a player's own turn as "this was really the GM's time, not theirs"); since `defaultCategory()` only ever hands out `"gm"` on its own to an already-unowned combatant, `ownerId` is only non-null here when a human explicitly overrode a segment that technically belonged to someone, and a genuinely unowned `"gm"` segment (`ownerId` already null) falls straight through to the same defeated-redirect check as any other unclaimed segment. A hidden entity a player's client can't see full data for (no `ownerId`, no `actorType`) resolves exactly the same way an ordinary unclaimed NPC does — there's no separate "unknown" state.
- **`perCombatantStats()`**: `category === "player"` or `"gm"` segments with combat context, grouped by `effectiveOwner()` — `"gm"` is included alongside `"player"` specifically so a defeated, genuinely-unowned combatant's instant-skip (still category `"gm"`, its own default) can still be redirected here by `effectiveOwner()` instead of being dropped. Segments with no resolvable owner (a true, unclaimed NPC turn, or a manual GM recategorization) are skipped here — they belong to `gmTotalStats()`/`npcAggregate()` instead. Splits each owner's time into `inTurnMs` (time during a turn slot they were structurally designated for — see Timing statistics) and `outOfTurnMs` (time reassigned to them from someone else's slot — an Attack of Opportunity, or a redirected defeated NPC); `byEntity` further breaks `inTurnMs`/`outOfTurnMs`/`pausedMs`/`turnCount` down per `combatantId` (keyed by the segment's *own* `combatantId`, not the slot's — an out-of-turn credit's entity is whichever combatant actually did the acting), so a player controlling multiple combatants (character + summons) is shown per-entity in `buildBarsContent()`'s stacked bar instead of only merged into one number. `pausedMs` (both the owner-level and per-entity figure) surfaces as the amber portion of that bar's indicator row. `turnCount` (and `byEntity[].turnCount`) still only increments for a slot-opener that's specifically `category === "player"` (not `"gm"`) and `isRealTurn()`, so neither a redirected defeated NPC nor a manual GM recategorization of someone's own turn-opener can inflate anyone's turn count even though the former's time now counts toward their total.
- **`npcAggregate()`**: a genuinely unowned creature's own turn segments (`seg.ownerId == null`, `category === "player" || "gm"`, gated on `hasCombatContext()`, and `effectiveOwner(seg) === null` — claimed time, e.g. a redirected defeated instant-skip, belongs to `perCombatantStats()` instead). The explicit `ownerId == null` check (not just `effectiveOwner`) is what keeps a technically-owned segment a human manually flagged `"gm"` out of this total — that's GM administrative time, not "a monster's turn", even though its `effectiveOwner()` is also null. Uses `isRealTurn()` to gate its own `turns` counter — an unclaimed defeated NPC's instant-skip duration still counts toward `totalMs` (so its time doesn't vanish from the GM's "Monsters total" either), it just never counts as one of the turns the average divides by.
- **`countsForGM(seg, lastLiveOwner)`**: shared by `gmTotalStats()` and `gmRoundStats()` — `effectiveOwner(seg) === null` (not claimed by, or redirected to, an actual player) AND either `category === "gm"` (covers both a genuinely unowned combatant's own turn and a manual recategorization — `effectiveOwner()` already makes sure a manual one can't fall back to its technical owner) or `category === "player" && hasCombatContext(seg)` (the lingering unclaimed-`"player"`-category case from `defaultCategory()`'s pause carry-over, or from data that predates the `"gm"` default).
- **`gmTotalStats()`**: sums `countsForGM()` segments into `totalMs` and a per-`combatantId` `byEntity` (`{ combatantId, name, ms }`, `null` key for a no-combatant `"gm"` segment) so `buildBarsContent()` can render the GM bar as a stack of per-monster segments the same way it does for a player's controlled entities. Carries no turn count of its own — see `gmRoundStats()` in Timing statistics for how the GM's per-round average is computed instead.
- **`categoryTotals()`**: raw per-category sums for `team`/`setup`, independent of any specific person — `"gm"` isn't tracked here, since `gmTotalStats()`/`countsForGM()` cover it. Deliberately has no `defeated` filter at all — unlike the functions above, a `team`/`setup` segment isn't about per-owner turn-taking, so it just counts, defeated or not. Also deliberately not gated on `hasCombatContext()` — `setup` time commonly has no combatant at all (pre-combat prep, between-encounter housekeeping), and that's exactly the time this category exists to capture.

## Timing statistics

- **`buildTurnSlots()`**: partitions the *entire* selected session's timeline (not per-owner) into consecutive turn slots. A slot starts at every segment with `trigger === "turn"` or `"resume"` (a genuine new turn beginning) and absorbs every following segment — `pause`/`unpause`/`split`, or a segment reassigned to someone else — until the next trigger. The very first segment always opens slot 1; trailing segments after the last trigger (including the live running one) stay in the last slot. Each slot's `designatedOwner` is the *technical*, non-overridden `ownerId` of whoever's turn it structurally was (`null` for an NPC/monster turn) — reassigning a segment inside a slot never changes who the slot belongs to structurally, it only moves that segment's *time* to a different person's bucket via `resolvedOwner()`.
- `perCombatantStats()`'s `turnCount` (and `byEntity[].turnCount`) counts slots by `designatedOwner`, gated on the slot's opening segment being `isRealTurn()` and `category === "player"` — so reassignment (and a redirected defeated NPC) can inflate someone's *time* but never their turn count.
- **`ownTurnSlotsByOwner()`**: shared by `betweenTurnStats()` and `turnWindowStats()` — each player's own real turn-opening slots (`designatedOwner` set, opening segment `category === "player" && isRealTurn() && isTurnStart()`), grouped by owner, plus the whole session's start/end span both need for their "before the first turn" / "after the last turn" edge handling.
- **`turnWindowStats()`**: for each player, fences their entire credited timeline (`"player"`- or `"gm"`-category segments `effectiveOwner()` resolves to them, same set `perCombatantStats()` uses) into one window per turn — a turn's window runs from the end of their previous turn (or the session start, for their first) through the end of that turn, and the last turn's window absorbs everything through the end of the session instead of stopping at its own end. Because these windows partition the player's whole credited timeline (in-turn and out-of-turn time both) with no gaps or overlaps, the average across them (`avgMs`) always multiplies back out to exactly `perCombatantStats()`'s `totalMs` for that player — unlike a plain `inTurnMs / turnCount` average, which disagrees with the total the moment the player has any `outOfTurnMs`. This is what the chat bars and player list show as their "Ø …/round" figure (in ordinary play — one turn per combatant per round — a player's own turn-cycle window lines up with the actual combat round, hence the label).
- **`gmRoundStats()`**: the GM's equivalent average, but per Foundry combat *round* rather than per individual monster turn — the GM has no single "own turn" the way a player does. Every segment already carries the `round` it was created in, and rounds are already a contiguous, gapless partition of the whole session, so grouping `countsForGM()` segments by that field directly is the fencing, with no boundary math needed. A round with no GM-attributed time still counts in the denominator (a quiet round still happened).
- **`betweenTurnStats()`**: for each `designatedOwner`, the average gap between the end of one of their turn slots and the start of the next. Only slots whose opening segment is `category === "player" && isRealTurn()` are considered — a slot's `designatedOwner` comes straight from the opening segment's raw `ownerId` regardless of category, so a stray non-turn blip (a tracker mis-click that briefly shows a real player as current combatant, then reverts) would otherwise still count as one of "their" turn boundaries and slice one genuine gap into two much smaller fake ones, dragging the average down. The time before their very first (real) slot plus the time after their very last one is combined into **one extra synthetic gap** ("wraparound") before averaging — a boundary fragment alone is biased by seat/turn-order position, but the combination of both reconstructs something equivalent to one full real gap, included as exactly one additional sample. This also means someone with only a single turn slot still gets a usable average instead of "no data".
- **`absoluteWaitStats()`**: session span minus a player's own active time, where "active" is `inTurnMs + outOfTurnMs` combined (both mean "not idle", regardless of whose slot the time technically fell in). `setup`-category segments are excluded from active time but stay inside the span, so setup time reads as wait time for *every* player. `team`- and `ignore`-category segments are cut out of the span itself, so that time is invisible to individual wait entirely — `team` shows up via `categoryTotals().teamMs` / the Team bar instead, `ignore` shows up nowhere by design. Keyed by `effectiveOwner()` (so a redirected defeated NPC's time reduces that player's wait too, same as any other active time) across all `"player"`- or `"gm"`-category segments with combat context — not by turn slots, so a player who only ever received reassigned or redirected time and never had their own designated turn still gets a real wait figure instead of being missing from the map.
- **`sessionTotalMs()`**: first segment start to last segment end (or now) across the whole selected session, minus any `ignore`-category time — "how long this took overall". Excluding an ignored segment from the min/max span wouldn't shrink it by itself (segments before and after still anchor the same start/end), so its duration is explicitly subtracted. Not the same span `absoluteWaitStats()` uses internally (that one also excludes `team` time); the two can legitimately differ.
- **`formatDuration(seconds)`**: renders `>=60s` as `XmYYs`, otherwise `Ys`. Used everywhere a duration is displayed, in both the panel and chat reports.
- **`escapeHtml(s)`**: escapes `& < > " '`. Every name interpolated into `innerHTML` or `ChatMessage` content goes through it — token/actor/user names are renamed by anyone with permission, and both the panel's `innerHTML` and chat content (post "Reveal to Everyone") render whatever's in them to other clients.

## Rendering

- The panel is a hand-built `<div id="combat-timer-panel">`, not a Foundry `Application`/`ApplicationV2`. Both the panel's own width and the segment pane's height are user-adjustable and persisted (`ui.panelWidth`, `ui.segHeight`); width defaults to 300px and is clamped to `[PANEL_WIDTH_MIN, PANEL_WIDTH_MAX]` (and the viewport). The width handle (`#ctp-resize-w`) sits on the left edge and keeps the panel's current RIGHT edge fixed on screen while dragging, regardless of anchor mode - when right-anchored (`ui.left === null`) that already falls out of a plain width change via CSS `right`, but when explicitly left-positioned, `ui.left` has to be adjusted in lockstep too or the handle wouldn't track the cursor at all.
- **Section order is the reading order, and is load-bearing:** header → `ctp-menu` → `ctp-settings` → `ctp-tabs` → `ctp-archive-list` → `ctp-live` → `ctp-summary` → `ctp-filters` → `ctp-segments` → `ctp-resize` → `ctp-post-menu` → post button → `ctp-toast`. The session tabs sit *above* everything they scope (they previously sat below the data they controlled, next to the split button), and the segment list — the only editable surface — gets the largest, resizable share of the height. `ctp-settings` (tracking-threshold steppers, opened from the ⋯ menu's "Settings" entry) sits directly below `ctp-menu`, the same way `ctp-archive-list` sits directly below the `ctp-tabs` control that opens it.
- `renderPanel()` runs on a 1-second `setInterval` and calls one renderer per section (`renderMenu`, `renderTabs`, `renderArchiveList`, `renderLive`, `renderSummary`, `renderFilters`, `renderSegments`, `renderPostMenu`). Each fully replaces its own section's `innerHTML` and rebinds listeners — there is no diffing.
- **`renderSegments()` is the exception, and must stay one.** Replacing `#ctp-segments`'s children resets `scrollTop` and destroys any text selection, so doing it every second made anything below the fold unreachable during live combat. `segmentSignature()` builds a string from everything that affects the markup (selected session, filter, expanded group keys, open pickers, and each segment's id/category/`overrideOwnerId`/`defeated`/`combatantName`/`end`); when it matches the previous tick the rebuild is skipped and only the two things that actually tick — `[data-live-dur]` and `[data-group-dur]` — are patched via `textContent`. Any new piece of segment-list state must be added to the signature, or it will silently fail to render until something else changes.
- `persist()` is called at the top of every `renderPanel()` tick (plus at explicit mutation points like segment reassignment), so state loss on an unexpected reload is bounded to under ~1 second. `syncCombatantNames()` runs right before it on the same tick: some modules hide an NPC's real name until a reveal condition is met, then rename the combatant, and `combatantName` is otherwise only ever captured once at segment creation (see Segment above) — this compares every live combatant's current name against what's stored on that combatant's segments in the currently tracked session and overwrites them in place on a mismatch. Limited to the live combat; an archived session's combat no longer exists to compare against.
- **Panel layout state is stored separately from tracking data**, under `localStorage["ctp-ui-<world.id>-<user.id>"]` (`{ left, top, panelWidth, segHeight, summaryOpen, maxArchivedSessions, shortPauseMergeThresholdMs, setupPauseThresholdMs }`, see `persistUi()`). Deliberately not part of the tracking blob: corrupt or absent UI state must never be able to take session data down with it. `left: null` means "unpositioned", i.e. anchored to `right: 16px`. Three of these feed back into tracking behavior rather than being purely cosmetic — `maxArchivedSessions` (default 10, via `enforceArchiveCap()`), `shortPauseMergeThresholdMs` (default 3000, `closeSegment()`'s pause-noise-merge cutoff) and `setupPauseThresholdMs` (default 5000, passed into `defaultCategory()` as its `threshold` parameter) — still kept here rather than in the tracking blob, since a corrupt/absent UI key falling back to the default is harmless, unlike corrupt tracking data. The latter two are adjustable via the ⋯ menu's "Settings" entry (`renderSettings()`), the same −/+ stepper pattern `maxArchivedSessions` established.
- Drag (header) and resize (`ctp-resize`) both use pointer events with `setPointerCapture`, suppress `document.body.style.userSelect` for the duration, and persist on release. `clampPanelPosition()` runs on every move *and* on load — a panel dragged to the edge of a wide monitor must not end up off-screen on a laptop.
- `ctp-live` is the live-tracking surface: round/turn position, session total, the running segment with its owner and duration, and the ✂️ split button *next to the thing it splits* (it used to sit in a strip with the session tabs, implying it was tab-scoped). When viewing an archived session it shows that session's start time (see "Session and history" above — archived sessions are labeled by when the combat started, not ended) and no split button — split always acts on live tracking regardless of what's being viewed, so offering it there was misleading. A selected archived session whose manifest entry has since been deleted (a narrow race between two actions) falls back to a "this archived session is gone" message instead of throwing.
- `ctp-summary` has two states, persisted via `ui.summaryOpen`. Collapsed: a proportion strip (one slice per entry, `min-width:3px`, name/time/percentage in a `title` tooltip) plus the top three by name. Expanded: a labelled mini-bar per entry. The strip does not try to identify anyone — it answers "was this fight lopsided", and the expanded state is the labelled view. Its entries come from `summaryEntries()`, shared with `buildBarsContent()`, so the panel and the chat report can never disagree about who is in the session.
- `#ctp-segments` shows the entire selected session (no cap), newest first, grouped into turn slots by `buildDisplayGroups()`. That is deliberately **not** `buildTurnSlots()`: that one drops `"ignore"` segments entirely (correct for statistics, useless here — you could never un-ignore one) and its slots aren't keyed for a stable DOM identity. A display group is keyed by its opening segment's id, and a group holding exactly one segment renders as a single row carrying the category chip directly, rather than a header plus an identical child. Groups are collapsed by default; the live group, and every group while a filter is active, are force-expanded. `🔄 ROUND N` markers are emitted as the reversed walk crosses a round boundary, and only when `round` is populated. A collapsed multi-segment group otherwise attributes its whole total to the opening segment's name and color, even when some of its other segments carry a different category or effective owner (e.g. a monster's opportunity attack recategorized to `"gm"` mid-turn) — `groupHTML()` renders a small inline composition chip (reusing `proportionalSegmentsHtml()`, same as the chat report bars) whenever that's the case, colored the same way a segment's own dot/chip would be, so the collapsed row hints at the mix without needing to expand it.
- **`segmentDisplayName(seg, technicalName, fallbackWho)`**: shared by `segRowHTML()` and both branches of `groupHTML()` — decides what a row's primary/secondary name display should be. `"player"` segments (and a genuinely unowned combatant's own `"gm"` turn — still real activity, just landing in the GM bucket) read primarily as whoever it's now credited to (the technical combatant, or `ownerName(overrideOwnerId)` if manually reassigned), with the pre-reassignment combatant demoted to a muted `(from …)` note instead of the reverse — showing the original combatant as primary would read as "still theirs" even though the time isn't. Any other category (`"setup"`/`"team"`/`"ignore"`, or a `"gm"` recategorization of a segment that still has a real `ownerId`) isn't that combatant's own activity at all, so the category's own label (`CATEGORY_META[category].label`) becomes the primary text instead, with the technical combatant as the `(from …)` note — a monster's turn split off as GM rules-lookup time reads as "GM", not as if the monster were still doing something. Every truncatable name span in the panel (`text-overflow:ellipsis`) carries a matching `title` with the untruncated text, including this row's combined primary+origin string.
- Expanding a group scrolls its last row into view (`scrollIntoView({block:"nearest"})`) right after the click, instead of leaving the view anchored on the header with everything newly revealed hidden below the fold - `renderSegments()`'s own per-tick anchor-preserve logic (which the click's `renderPanel()` call also runs) is deliberately overridden immediately afterward for this one interaction. Opening `categoryPickerHTML()`'s category chips (or, from there, its player-list chips) does the same for the same reason, scrolling the segment's/group's anchor wrapper's current last child into view - the wrapper's attribute (`data-anchor-seg` vs. `data-anchor-group`) has to be read from the click's own ancestor chain before the rerender, not guessed from the id afterward, since a multi-segment group's *opening* segment carries both (the collapsed/expanded header's `data-anchor-group`, and its own `data-anchor-seg` once rendered as a child row) under the *same* id.
- Category editing is two-step: each segment row shows its current category as a labelled chip (`CATEGORY_META[key].label`/`bg`/`fg` — each category has its own color, and text labels replaced the five permanently-rendered emoji buttons, which were ambiguous: 🧑 meant both "player-controlled" and "category: player"). Clicking the chip opens the five-way picker (`openCatSegId`); choosing "Player…" opens the player list (`playerPickerSegId`) rather than assigning immediately, so time can go to somebody other than the technical owner.
- `segFilter` (`"all" | "setup" | "reassigned" | "long"`) filters the segment list only. `"reassigned"` matches `overrideOwnerId`, `category === "team"`, or `category === "gm"` **with** `ownerId` set — that last condition specifically excludes a genuinely unowned combatant's own turn (also `"gm"` by default, per `defaultCategory()`, but that's every routine monster turn, not a manual intervention worth surfacing). A filtered group renders auto-expanded and non-matching groups are dropped entirely — hiding a match behind a collapsed header would defeat the point of filtering for it.
- **No `alert()`/`confirm()` anywhere.** A native dialog steals focus from Foundry (which listens for keybinds globally) and looks nothing like the panel. `toast(message, actionLabel?, onAction?)` and `confirmBar(message, confirmLabel, onConfirm)` both render into `#ctp-toast` at the bottom of the panel.
- `exportSelectedSession()` / `importSessionFromFile()`: export operates on whichever session is currently selected (`selectedSession`) — downloads a JSON file (`{ v: 1, exportedAt, world, session, startedAt, endedAt, segments, currentSegment }`) via a throwaway `Blob`/`<a download>`. Import reads a file picked through a hidden `#ctp-import-file` input, validates only that `segments` is an array, then behaves according to `importMode` (set right before the input is clicked — see `renderMenu()`): `"replace"` (the long-standing default) **replaces** whichever session is currently selected outright, after a `confirmBar()`; `"new"` always adds the file as a brand-new archived entry via `addArchivedSession()` regardless of what's selected — this is what replaced the old "select an empty archived slot to import into it" path, since a manifest of only-ever-real entries has no such empty slot anymore. Imported segments are used as-is — no backfilling for a field an older script version's export might be missing; this script only supports data it wrote itself. `importUndo` snapshots what was replaced (or, for `"new"`, just the new entry's id) immediately before the change, and the success toast offers a one-shot "Undo" (`undoImport()`) — one level deep, in memory only, for the lifetime of the page; undoing a `"new"` import deletes that manifest entry and its storage key outright, the same as a manual delete. Importing into `"current"` calls `reconcileWithLiveState()` immediately afterward, since the imported `currentSegment` (if any) has no guarantee of matching whatever's actually live right now.
- The `⋯` header menu (`ctp-menu`) holds everything rare: new session, delete archived session (only shown when an archived session is selected), export, import (replace), import as a new archived session, undo import (only when a snapshot exists), dummy data, reset panel position. This replaced a permanently-visible 🆕/🗑️ header icon whose meaning flipped based on which session was selected — a destructive mode switch driven by a control the user wasn't looking at.
- The "Post report" menu (`ctp-post-menu`, `postMenuOpen`) is normally a flat list that posts straight to chat on click, like the `⋯` menu. "Recent combats" is the one exception: clicking it doesn't post - it flips `recentComparePicking` and `renderPostMenu()` swaps the same section's content for `renderRecentComparePicker()`'s window-size buttons (`reachableCompareWindows()` computes which fixed sizes are actually reachable) instead of re-rendering the report list. `recentComparePicking` is reset to `false` every time `postMenuOpen` goes false (checked at the top of `renderPostMenu()` itself, not scattered across every place that can close the menu), so a stale sub-view never lingers into the next time the button's clicked. The option itself is dimmed/inert (no `data-hover`, no click handler runs) when `archiveManifest.length === 0` - there's nothing to compare "Tonight" against yet.
- `panel` is declared as a bare `let panel = null` **before** `buildPanel()` is called, not as `let panel = buildPanel()`. `buildPanel()` assigns to `panel` while it runs (`applyPanelPosition()` has to measure the real element), which would hit the temporal dead zone if the binding were created by that same call's initializer.

## Chat output

`buildBarsContent()`, `buildPlayerListContent()`, `buildRoundPacingContent()`, `buildFunFactsContent()`, `buildGmOverheadContent()`, `buildRecentComparisonContent()`, and `buildPauseSummaryContent()` each return a standalone HTML string (see hard constraint #2 for the styling rules), built via a shared `wrapCard({ title, subtitle, body })` — the card container, header line, and "No data" fallback are written once, so the `!important` hardening only has to be kept correct in one place. All seven are posted via `postToChat(content, kind)`:
```js
ChatMessage.create({
  content,
  speaker: ChatMessage.getSpeaker({ alias: "Combat Timer" }), // not the default - avoids posting under whatever token happens to be selected
  whisper: [game.user.id],
  flags: { "combat-timer": { kind, session: selectedSession, at: Date.now() } }, // kind: "bars" | "players" | "rounds" | "facts" | "gmoverhead" | "recent" | "pauses"; lets a future feature find/identify its own past reports
});
```
Always self-only ("self roll" semantics) — there is deliberately no in-panel "reveal to everyone" button; Foundry's own chat-message context menu already offers "Reveal to Everyone" for any message the current user authored and whispered to themselves, so it isn't reimplemented here.

- `buildBarsContent()`: one bar per entry returned by `summaryEntries()` — players (via `perCombatantStats()`), one combined "GM" bar (`gmTotalStats()`), a "Team" bar (`TEAM_COLOR`, anthracite) and a "Setup" bar (`SETUP_COLOR`, neutral grey) whenever those categories have any time at all. Setup previously reused `getCombatantColor(null)`, i.e. the GM's own color, which made two adjacent bars in the same report identical and unidentifiable — all sorted together by total time descending, not shown separately or omitted when zero. Each bar's duration line also shows its percentage of `sessionTotalMs()`, plus a per-player "Ø …/round" from `turnWindowStats()` or a GM "Ø …/round" from `gmRoundStats()` when there's more than zero turns/rounds to average over (see Timing statistics); the bar itself stays scaled to the longest bar (`max`), not to the session total — scaling to the session total would make every bar too short to read once there are several categories.
  - `buildPlayerBarRows()` first runs a player's `byEntity` through `mergeAlienEntities()`: an entity with no `inTurnMs` of its own under this owner never had a genuine designated turn - it's only present because some of its time was redirected here (e.g. an Attack of Opportunity credited from a monster's turn) - so it gets folded into the primary entity instead of standing out as its own shaded segment in the main bar. The main bar should only visually split entities the player actually, structurally controls (their own PC plus any of their own summons/pets with a genuine turn); a pure redirect's out-of-turn/paused time still shows up correctly in the indicator row below, just merged into the primary's own column rather than getting a separate one. If NO entity has any `inTurnMs` (this owner only ever received redirected time), nothing is merged - there's no genuine "owner entity" to fold into.
  - A player's or the GM's bar is a stack of solid, per-entity segments (`byEntity`/`gmTotalStats().byEntity`) via `orderAndShade()` + `darkenHex()`: the "primary" entity (a player's own `actorType === "character"`; for the GM, just the last entity in turn order, since there's no PC to anchor on) renders in full color and sits rightmost, every other entity trails to its left in progressively darker shades of the same base color, in their original turn-order sequence. Labels are two-tier: a segment carries the entity's *name* at `labelPct` (28%) or better, falls back to its duration at `minLabelPct` (12%), and goes unlabelled below that — a narrow sliver still renders at its correct proportion. Label color comes from `labelColorOn()` (WCAG relative luminance of the fill), not a fixed value: segments are shaded down to 45% of the base color, so the old hardcoded `rgba(0,0,0,0.55)` was unreadable on roughly half of them. `capEntities()` caps a stack at `MAX_BAR_ENTITIES` (4), merging everything past it into a single `+N more` item placed first so it takes the darkest shade at the far left — past four or five entities the 0.45→1.0 shade spread puts neighbouring segments within ~8% brightness of each other and the bar reads as one smear. With exactly one entity this degenerates to exactly one full-width, unlabeled segment — pixel-identical to the plain bar every entry used to always render.
  - When a player has any `pausedMs` or `outOfTurnMs`, a second, 4px indicator row appears directly under the main bar, using the *same* per-entity column widths so a mark always lines up under the segment it describes. Each column is further split into paused (`#e8a33d`, fixed and entity-independent — the same color means the same thing everywhere in the report) / out-of-turn (`#4fc3d9`, likewise fixed) / in-turn (the entity's own shaded color) — in that order, left to right, so the exceptional portions are the first thing seen entering each column rather than trailing at the far edge. Patterns (stripes/dots) were tried first and rejected — at 4-6px tall they read as uneven darkening, not a shape, not distinguishable from each other. The GM bar never gets this row; only players track paused/out-of-turn time. Whenever at least one indicator row was rendered, a one-line legend with two colour swatches is appended to the card — the two fixed colours mean nothing to someone who hasn't read this file, and after "Reveal to Everyone" that's most of the people who see it.
- `buildPlayerListContent()`: one stacked block per player (name on its own full-width line, three stats — avg turn / avg gap / total wait — on the line below), sorted by total time descending — the same order as `buildBarsContent()`, so the two reports line up when read side by side. Deliberately `<div>`-based, not a `<table>`, both to avoid host CSS leakage and because a 4-column table didn't fit Foundry's narrow chat sidebar without wrapping. A single tiny legend line follows the last row (only when there's at least one, i.e. not shown alongside the "No data" fallback) clarifying that Turn/Gap are averages and Wait is a total.
- `bucketTimeByOwner(segs, lastLiveOwner)`: the shared bucketing pass under both `roundPacingStats()` and `sessionCompareStats()` — same ownership rules `summaryEntries()` uses for the main chart (player/GM via `countsForGM()`/`effectiveOwner()`, plus Team/Setup as their own buckets), keyed by ownerId or the sentinel `"gm"`/`"team"`/`"setup"` (a real Foundry user id never collides with those). `lastLiveOwner` is passed in rather than recomputed, so a caller can resolve "last real owner" over a wider span than the segments actually being bucketed — `roundPacingStats()` resolves it across the whole session but buckets one round's segments at a time, while `sessionCompareStats()` resolves and buckets each session independently, since sessions don't share history.
  - `roundPacingStats(segs)`: partitions a session into rounds (segments with `round == null` skipped — no round to attribute them to, so an all-skipped round produces no entry at all, same as it stays invisible to `gmRoundStats()`'s round count) and buckets each via `bucketTimeByOwner()`. Kept ownerId-only (no name/color) so it stays pure/game.users-free; `init()` resolves display info via `ownerKeyDisplay()` (below).
  - `sessionCompareStats(sessions)`: one `{ id, totalMs, byKey }` per `{ id, segs }` input — `totalMs` comes from `sessionTotalMs()` itself (matching what every other report already calls "this session's total"), not the sum of the bucketed time.
- `ownerKeyDisplay(key)` / `ownerBucketParts(byKey)` / `ownerBucketBarRow(label, ms, byKey, pctOfMax)`: the shared rendering pipeline for any `bucketTimeByOwner()`-shaped breakdown, used by both `buildRoundPacingContent()` and `buildRecentComparisonContent()`. `ownerKeyDisplay()` resolves a bucket key to a name/color the same way `summaryEntries()` does for `perCombatantStats()`/`gmTotalStats()`/`categoryTotals()`. Unlike `buildPlayerBarRows()`/`buildGmBarSegments()`, these buckets are genuinely different people/categories, not shades of one owner's color — so each keeps its own real `getCombatantColor()`/`TEAM_COLOR`/`SETUP_COLOR` via `ownerBucketParts()`, with `capEntities()` reused only for its cap-and-merge behavior (no `orderAndShade()`/`darkenHex()`) and a fixed neutral grey (`OWNER_MERGED_COLOR`) for the merged "+N more" slice — `isPrimary` anchors on the largest contributor (the array is pre-sorted by `ms` descending before capping), unlike `buildGmBarSegments()`'s own "last in turn order" anchor, since pre-sorted input would otherwise merge away the largest items instead of the smallest.
- `buildRoundPacingContent()`: one row per combat round via `roundPacingStats()` + the shared rendering pipeline above, scaled relative to the longest round (`max`) so a round that ran long visibly reads longer than a quick one — the whole point of a pacing report.
- `buildRecentComparisonContent(n)`: one row per session (via `sessionCompareStats()` + the same shared rendering pipeline as `buildRoundPacingContent()`, just at session granularity), for "Tonight" (`recentSessionsForCompare()`'s label for the live session, whatever's actually selected in the panel) plus the `n - 1` most recently archived sessions — `archiveManifest` is already newest-first, so that's just its first `n - 1` entries, each loaded via `loadArchivedSessionSegments()` directly rather than through the single-entry `viewedArchive` cache (this needs several sessions' data alive at once, unlike everything else that only ever looks at one session). A short headline compares "Tonight"'s total against the average of whatever else is in the window. Unlike every other report, this one needs a second step before it can post — see `renderRecentComparePicker()`/`recentComparePicking` under Rendering for how the Post-report menu handles that.
- `buildFunFactsContent()`: a fixed six-tile grid built on the pure `funFactsStats(segs)` aggregator — longest/shortest turn (from `ownTurnSlotsByOwner()`'s own real turn-opening slots), slowest average (`turnWindowStats()`'s per-player Ø, the same figure the main chart already shows), longest wait plus the session average for scale (`absoluteWaitStats()`), and quickest/most "reactions" (a dedicated pass over `buildTurnSlots()` for a genuine out-of-turn credit — e.g. an Attack of Opportunity). A "reaction" specifically excludes a defeated NPC's instant-skip redirect via `isRealTurn()`: without that exclusion, an instant-skip's near-0ms duration would win "quickest reaction" every session regardless of what players actually did, since `effectiveOwner()`'s defeated-redirect makes it technically out-of-turn credit too. Each fact records only an ownerId (kept pure/game.users-free, same reasoning as `roundPacingStats()`); a fact with no qualifying data yet (e.g. no out-of-turn segments this session) renders as a muted "Not enough data yet" tile rather than being dropped, so the six-tile layout stays fixed regardless of what's happened so far.
- `buildGmOverheadContent()`: one bar decomposing `buildBarsContent()`'s combined GM bar into what it's actually made of, via the pure `gmOverheadStats(segs)` aggregator — genuinely unclaimed monster turns (`byMonster`, the same per-`combatantId` shape `gmTotalStats().byEntity` already returns, split out using the same `seg.ownerId == null` distinction `npcAggregate()` uses) vs. `manualMs` (a technically-owned segment a human recategorized `"gm"` — previously invisible as its own bucket, blended under whichever combatant it came from). `categoryTotals(segs).setupMs` is folded in as a third bucket. All three are shaded from the GM's own color via the *same* `orderAndShade()`/`darkenHex()`/`capEntities()` mechanism `buildGmBarSegments()` already uses, deliberately with no new color logic — Setup/"Manual GM" get no fixed color of their own here (unlike the main chart's standalone Setup bar), since this report's entire point is "all of it is GM overhead." The Setup/Manual pseudo-entities are placed ahead of the real monster entities in the array passed to `capEntities()`/`orderAndShade()` so the monsters still anchor the bright/rightmost end (`isPrimary` stays `() => false`, same as `buildGmBarSegments()` — deliberately *not* pre-sorted by `ms` beforehand, since that would break the "last entity in turn order is the anchor" convention `orderAndShade()`/`capEntities()` rely on when there's no real primary predicate; see `buildRoundPacingContent()`'s own comment for why pre-sorting needs a different `isPrimary`). A textual `Setup X% · Manual GM Y% · Monsters Z%` line (via the pure `pct()` helper) follows the bar, since a single bar alone is hard to read exactly once there are more than a couple of monsters.
- `buildPauseSummaryContent()`: three tiles (total paused time with the average pause length for scale, pause count, and the single longest pause with who was on the clock and its round) built on the pure `pauseSummaryStats(segs)` aggregator — a plain `trigger === "pause"` filter, independent of category, except `"ignore"`-category pauses are excluded (those exist specifically for a wall-clock gap that isn't real time, e.g. the session resumed days later, and would otherwise make "longest pause" a meaningless multi-day outlier). Needs no `ownerId`/color resolution the way the other reports' facts do — a pause segment's `combatantName` is already stored raw on it — so this is the only report aggregator that stays entirely pure with nothing left for `init()` to resolve.

## Multi-server support

`@match` in the userscript header is a plain static list — one line per Foundry server URL, no dynamic logic. Duplicate the line to add more.
